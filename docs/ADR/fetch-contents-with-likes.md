# コンテンツ一覧取得時の likes 件数の取り方

## 経緯

- 当初: `select=*,likes(count),profiles(...)` で PostgREST の埋め込み一括取得を使用
- 途中: コンテンツごとに `likes` を個別 count する N+1 方式へ変更（埋め込みで PGRST200 が出るため応急処置）
- 直近: レビュー指摘で N+1 を解消するため、再び埋め込み一括取得へ戻したところ PGRST200 が再発し、画像一覧が取得できなくなった

## 原因

`likes` は image / music の双方を 1 テーブルで扱うポリモーフィック設計（`content_type` + `content_id`）になっており、`content_id` には FK を貼れない（FK は単一テーブルしか参照できないため）。
PostgREST の埋め込み機能は FK をスキーマキャッシュから辿って自動 JOIN する仕組みなので、FK が無い `image_contents ⇄ likes` の埋め込みは成立しない。
当初コードはこの矛盾を抱えたまま呼び出し経路が未完成で発火していなかっただけ。

## 解決策（採用: 案A）

クライアント側で 2 リクエストに分けて取得し、アプリ側で集計する。

1. `image_contents` / `music_contents` を `select=*,profiles(...)` で取得（埋め込みは FK のある profiles のみ）
2. 取得した id 群に対し `from("likes").eq("content_type", ...).in("content_id", ids)` でまとめて取得
3. クライアントで `content_id` ごとに件数を集計して ContentItem に詰め直す

ラウンドトリップはコンテンツ数に関わらず 2 回固定。N+1 は発生しない。

## 不採用の選択肢

- **案B（VIEW を作る）**: DB 側に `image_contents_with_like_count` 等の VIEW を用意して 1 リクエストで取得。クライアントは `from("view名")` に変えるだけ。性能とコードの簡潔さで優れるが、DB 変更が伴うため今回は見送り。今回の修正後でも案A → 案B の移行は容易（クライアント呼び出しの差分が小さい / VIEW 追加は既存テーブルに影響を与えない）なので、必要になった時点で移行する。
- **案C（`image_likes` / `music_likes` にテーブル分離）**: FK を貼れるようになるが、likes 機能の追加・修正が常に 2 箇所必要、ユーザー単位の総合一覧取得に UNION が必要、コンテンツ種別追加のたびにテーブル増殖、と運用コストが高い。要件側で `likes` を 1 テーブルに統合する判断が既にされているため不採用。

## 今回 案A を選ぶ理由

- PGRST200 を最小修正で塞ぎたい（DB 変更を伴わない）
- 既存 Repository のシグネチャ・呼び出し側の改修が不要
- 案B への移行はいつでも容易なので、現段階で DB に手を入れる必然性が薄い
